# Voice pipeline: testing and improvement loop

How we test the spoken-order pipeline (ASR → parse → ERP match) and fold
failures back into it. Everything runs locally against cached ERP data;
**nothing here writes to ERPNext.**

## The pipeline under test

```
audio → Whisper (small, int8, CPU)        server.py:_transcribe_audio
      → hotwords + optional 2nd pass      server.py:_hotwords / _recognize_order_audio
      → text normalization                server.py:_normalize_transcript_text
      → fast local parse                  server.py:_fast_parse
        (aliases → pinyin/hanzi fuzzy → branch rescue)
      → LLM fallback (kimi/codex CLI)     only when fast parse gives up
```

The eval exercises ASR + fast parse. The LLM fallback is NOT tested here
(too slow) — so eval numbers are a lower bound on production accuracy.

## Key files

| File | Role |
|---|---|
| `customer_spoken_names.txt` | Curated dictionary: `customer_id` + `spoken_name` lines (multiple per customer). **Edit this** when a customer is said differently than their ERP name. |
| `voice_aliases.json` | Curated spoken→target map (items: `日晷园 → GH006-24`; customers: `熊进 → VIP熊进`). Highest parse priority. |
| `learned_aliases.json` | Machine-harvested mishearings (from `--harvest`). Same format family, checked after `voice_aliases.json`. |
| `customer_voice_focus.json` | Whisper hotword focus list, regenerated by each eval run from its failures (gitignored). |
| `voice_customer_eval/` | Generated audio + results (gitignored). |
| `recordings/` + `voice_log.jsonl` | Real user audio + transcripts (DEBUG_VOICE). The ground truth. |

## Resolution rules (user requirements)

- Customers sharing a spoken name (homophones 叁年间/三年间) → the one with
  the **newest ERP order** (`_customer_recent_order_rank`).
- Items sharing a spoken name across vintages → the **newest vintage**
  (`_vintage`).
- Never alias a phrase that is itself another customer's/item's spoken name
  (the harvest skips these automatically).

## Test suites

All in `voice_customer_eval.py`. Audio is synthesized once with edge-tts
(`zh-CN-XiaoxiaoNeural`) and cached by sentence hash, so re-runs are
ASR-only.

```bash
bin/python voice_customer_eval.py --suite customers   # every dictionary spoken name (734)
bin/python voice_customer_eval.py --suite items       # every catalogue spoken item name (158)
bin/python voice_customer_eval.py --suite random --seed 2 --random-count 100
bin/python voice_customer_eval.py --suite recent      # replay last 20 real ERP orders
bin/python voice_customer_eval.py --suite all         # customers + items
```

- **customers**: `{spoken}要{N}瓶{wine}` for each dictionary entry.
- **items**: fixed anchor customer （熊进） × each item spoken name — a failure
  isolates the item.
- **random**: random customer × curated item alias × random qty × random
  sentence pattern （要 optional, qty/item either order, 给…来…, paused
  commas). Closest to real dictation.
- **recent**: replays the last 20 ERP orders with shortest spoken names and
  real quantities (regenerate `/tmp/last20_orders.json` first — see below).

Useful flags: `--fresh` (ignore previous results), `--limit N`,
`--tts-only`, `--harvest`.

Each suite writes its own results file (`order_results.json`,
`random_results.json`, `recent_results.json`) so concurrent runs never
clobber each other.

## The improvement loop

1. **Run a suite.** Read the failures in the results file (`failures` key).
2. **Classify before fixing anything:**
   - heard correctly but not parsed → parser/alias problem (fix code/aliases)
   - misheard, in candidate list → picker/uncertain-flag territory
   - misheard badly → alias or normalization candidate
   - parse returned nothing → production would use the LLM; not a hard failure
3. **Harvest the mishearings:**
   ```bash
   bin/python voice_customer_eval.py --harvest
   ```
   Maps each heard phrase → expected target in `learned_aliases.json`,
   resolving shared phrases by the newest-order/newest-vintage rules and
   skipping unsafe collisions. Review the printed skip list.
4. **Stable mishearings of fixed vocabulary** （葡道→葡萄， 灵犀园→零西园…)
   belong in `_normalize_transcript_text` as regex rules — deterministic,
   no ASR needed. Prefer this over aliases when the mishearing is consistent.
5. **Re-run `--fresh`.** Alias harvest typically moves the customers suite
   several points; normalization rules fix whole classes at once.
6. **Real audio trumps TTS.** When `recordings/` + `voice_log.jsonl` show a
   real mishearing, add a dictionary entry or alias for it — TTS
   (XiaoxiaoNeural) is only a proxy for the user's voice.

## Refreshing the recent-orders suite

```bash
bin/python - <<'EOF'
import json, server
r = server.erp.call("GET", "/api/resource/Sales Order", params={
    "fields": json.dumps(["name", "customer"]),
    "order_by": "creation desc", "limit_page_length": 20})
orders, _ = server.erp_json(r)
out = []
for o in orders["data"]:
    r2 = server.erp.call("GET", f"/api/resource/Sales Order/{o['name']}")
    body, _ = server.erp_json(r2)
    doc = body.get("data", {})
    out.append({"name": o["name"], "customer": o["customer"],
                "items": [{"item_code": it["item_code"], "qty": it["qty"]}
                          for it in doc.get("items", [])]})
json.dump(out, open("/tmp/last20_orders.json", "w"), ensure_ascii=False, indent=1)
EOF
bin/python voice_customer_eval.py --suite recent --fresh
```

## SenseVoice experiment (not production)

`voice_sensevoice_eval.py` runs the same cached audio through SenseVoice
(sherpa-onnx, `models/`, gitignored, not in requirements.txt). Raw
SenseVoice beat raw Whisper (60.8% vs 54.5%) but lost to tuned Whisper
(67.2%). Its untested lever is native hotword biasing. Don't switch engines
until that's measured.
